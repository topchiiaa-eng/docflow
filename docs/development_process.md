# Процесс разработки «ДокПотока» с AI-агентами

Документация проектной работы: как AI-агент (Claude Code) использовался на каждом этапе, какие промпты давали результат, какие проблемы возникали и как решались. Проект вырос из шести домашних заданий курса — каждый этап ниже ссылается на соответствующий документ с деталями.

## Идея и её происхождение

«ДокПоток» — единая входящая лента электронных документов (ЭДО) для группы из нескольких юрлиц: лента с фильтрами и поиском, очередь «на подпись» с явным подтверждением по ролям, журнал подписаний, управление организациями и участниками, хранилище PDF. Идея — не выдуманная: у автора три юрлица в Контур.Диадоке, и до проекта мониторинг входящих решался Telegram-ботом (ДЗ-2). Продукт — это «рабочее место» вместо бота.

## Этап 1. Планирование

| Задача | Как использован AI | Результат |
|---|---|---|
| Генерация и валидация идеи | Обсуждение с агентом боли пользователя (обход N ящиков ЭДО), формулировка ценности в минутах | [ai-ui-homework/project_description.md](https://github.com/topchiiaa-eng) (ДЗ-3): проблема, ЦА, 4 функции MVP |
| Анализ конкурентов | Субагент-аналитик с веб-поиском (10 запросов): Диадок, СБИС, Такском, 1С-ЭДО, DocuSign, PandaDoc, Dext/Hubdoc | [competitors.md](competitors.md): ниша подтверждена (у провайдеров «несколько юрлиц» = переключатель, не лента), ценовой ориентир, главный риск — зависимость от API Диадока → решение сохранить абстракцию `EdoProvider` |
| UI-концепции (Text-to-UI) | 3 промпта → 3 самодостаточных HTML-макета разных стилей (минимал-почта, тёмный дашборд, ERP-таблица), рендер headless-Chrome | ДЗ-3 `ui_concepts/`: выбран «Дашборд» (master-detail) в светлой теме с табличным режимом из ERP-варианта |
| User Stories и ТЗ | Агент сгенерировал 12 историй с 31 критерием Given-When-Then; черновик ТЗ проверен **независимым агентом-«техлидом»** — 5 критичных пробелов (отсутствие мок-адаптера, неясная механика подписания и др.) → ТЗ v1.2 → v1.3 после ревью преподавателя | ДЗ-3 `technical_specification.md` v1.3 |

**Промпт, который сработал лучше всего:** ревью ТЗ в роли «придирчивого техлида, принимающего ТЗ перед передачей AI-инженеру» — агент нашёл то, что автор и первый агент пропустили (как второй пользователь попадает в аккаунт; на чём проверять J1–J2 без боевых ключей).

## Этап 2. Дизайн и архитектура

- **Архитектура данных** спроектирована агентом по ТЗ (промпт: «organizations ↔ org_members (роли) ↔ auth.users; documents → organizations; append-only sign_attempts; RLS: видимость только своих организаций; подписание только через RPC с проверкой роли»). Коррекции после ревью схемы: `security definer` для `is_member()` (иначе рекурсия RLS), права уровня колонок вместо широкой update-политики.
- **API** — PostgREST поверх таблиц + RPC (`sign_document`, `add_member_by_email`, `list_members`, `health`); контракт описан в `backend_documentation.md`.
- **Ключевое архитектурное решение** — интерфейс `EdoProvider` (`src/types.ts`): фронтенд не знает, откуда данные. Реализации: `mockProvider` (демо, тесты, CI без секретов) и `supabaseProvider`. Благодаря этому бэкенд подключался без изменения компонентов, а анализ конкурентов (риск одного провайдера) лёг на уже готовую абстракцию.

## Этап 3. Frontend

- **Инициализация** — `npm create vite@latest` + Tailwind v4 + Vitest, конфиги сгенерированы агентом; правила проекта `CLAUDE.md` (адаптация файла правил из ДЗ-2: `any` запрещён, 4 состояния экрана обязательны, подписание только через диалог, тесты по ролям).
- **Компоненты** — RTCF-промпты (Role-Task-Context-Format из ДЗ-2); каждый экран обрабатывает loading / error / empty / success.
- **Отладка с AI — реальный баг:** бесконечный цикл загрузки. Скриншот показал вечный спиннер, консоль — бесконечный поток `listIncoming failed`; диагноз агента: дефолт пропа `provider = createMockProvider()` создавал новый объект на каждый рендер → `useEffect` зацикливался; исправление в 3 строки. 12 тестов этот баг не ловили (они передавали стабильный проп) — вывод: запуск реального приложения обязателен.
- **Проектная доработка:** HashRouter (GitHub Pages без SPA-fallback) и 4 экрана — Входящие, На подпись, Журнал, Организации; формы с клиентской валидацией, зеркалящей check-constraints БД; загрузка PDF в Supabase Storage.

## Этап 4. Backend и инфраструктура

- **Выбор:** Supabase вместо self-hosted — через жёсткие ограничения (нет прав администратора → нет Docker; нет VPS). Метод из ДЗ-1: сначала отсечь по ограничениям, потом сравнивать.
- **Миграции** (5 файлов, `supabase/migrations/`): схема+RLS → журнал отказов → фиксы аудита + health + логи → CRUD/участники/Storage → политика владельца.
- **Отладка на живом бэкенде — три кейса, не воспроизводимых локально:** (1) SQL выполнился успешно, а кириллица в базе оказалась испорчена — `pbcopy` без UTF-8-локали; найдено сравнением `repr()` строк из API; (2) отказы не попадали в журнал — `raise exception` в plpgsql откатывал `insert`; исправлено возвратом `{ok,error}`; (3) `42P13` при смене типа результата функции — HINT сервера дал решение.
- **Кейс №4 (проектная работа): баг, которого не видят ни мок, ни 43 теста.** E2E-скрипт на живом бэкенде: создание организации → `42501 new row violates row-level security policy`. Причина: PostgREST делает `INSERT … RETURNING`, а PostgreSQL проверяет SELECT-политику на возвращаемую строку **до** срабатывания AFTER-триггера, делающего создателя участником, — политика «члены видят свои организации» в этот момент ещё ложна. Исправление — миграция 5: политика «владелец видит свою организацию». Мок-провайдер и компонентные тесты прошли зелёными, потому что у них нет RLS; поймал только сценарий против реальной базы.
- **Интеграции:** Google OAuth через Supabase Auth (PKCE), Яндекс.Метрика (12 событий воронки), Supabase Storage (приватный bucket, политики по членству в организации).

## Этап 5. Деплой, безопасность, качество

- **CI/CD:** GitHub Actions → GitHub Pages: audit → oxlint → prettier → tsc → vitest → build → deploy → smoke-check. Пайплайн дважды остановил деплой по делу (Pages не включён; файлы отредактированы в обход prettier).
- **Аудит безопасности** независимым AI-агентом по OWASP: 12 находок, 11 исправлено — в т.ч. серьёзная (`seed_demo_data` вызываема через RPC любым клиентом). При добавлении роутера `npm audit` нашёл транзитивную `undici` (high) — `npm audit fix` → 0. Отчёт: `security_audit.md`.
- **Мониторинг и логи:** health-check RPC, uptime-workflow с алертами, структурированные JSON-логи с централизованным хранением в `client_logs`, промпты для AI-анализа логов.
- **Оптимизация с AI:** разделение чанков (supabase-js отдельно — 55 КБ gzip кэшируется независимо от кода приложения), стабильные ссылки для `useMemo`, отмена устаревших ответов в эффектах — всё найдено линтером/агентом.

## Проблемы и решения (сводная таблица)

| Проблема | Этап | Решение |
|---|---|---|
| Бесконечный цикл загрузки (нестабильный дефолт пропа) | Frontend | Диагностика по скриншоту + консоли; провайдер — синглтон модуля |
| Headless-скриншоты ловили loading-state (HMR-вебсокет не даёт «затихнуть») | Frontend | Скрипт на puppeteer-core с явным `waitForSelector` |
| Испорченная кириллица в БД при успешной миграции | Backend | UTF-8-локаль перед `pbcopy`, проверка данных обратным чтением |
| Отказы не попадали в журнал (`raise exception` откатывает insert) | Backend | RPC возвращает `{ok, error}`, клиент сам бросает ошибку |
| Служебная функция вызываема через RPC (DoS квоты) | Безопасность | `revoke execute … from public` для всех служебных функций |
| Тестовые пароли в репозитории | Безопасность | Ротация, `.env.test.local`, учётки — только в тексте сдачи |
| CSP блокировала websocket и iframe Метрики | Интеграции | Точечное расширение `connect-src`/`frame-src` вместо «разрешить всё» |
| RLS отклоняла создание организации (RETURNING проверяется до AFTER-триггера) | Backend | Политика SELECT для владельца (миграция 5); найдено e2e на живой базе |
| Деплой упал на `prettier --check` после правок через `sed` | CI/CD | Правка файлов только через форматтер; правило в памяти проекта |

## Выводы и рекомендации

1. **AI-агент сильнее всего там, где его работу проверяет другой агент или реальный запуск.** Лучшие находки проекта — от независимого ревью ТЗ, независимого аудита безопасности и API-тестов против живой базы, а не от первичной генерации.
2. **«Зелёный прогон» ≠ «работает».** Три самых серьёзных бага (цикл загрузки, испорченная кириллица, пустой журнал отказов) прошли через зелёные тесты и «Success» миграции. Проверять нужно данные и побочные эффекты другим инструментом, чем тот, что породил результат.
3. **Правила проекта (`CLAUDE.md`) влияют на архитектуру, а не на форматирование.** Из правила «чистая логика без сети» выросли `commands.py` (ДЗ-2) и `src/lib/*` с тестами; из правила «подписание только через диалог» — RPC с проверкой роли на уровне БД.
4. **Жёсткие ограничения — лучший фильтр решений.** Нет прав администратора → Supabase, GitHub Pages, puppeteer с системным Chrome; каждое из этих решений оказалось проще и надёжнее альтернатив.
5. **Рекомендация:** закладывать в процесс отдельный шаг «независимое ревью сгенерированного» (ТЗ, схема, код, безопасность) и держать абстракцию над внешним провайдером — она дважды спасла проект (мок для тестов/CI и ответ на риск зависимости от Диадока).
