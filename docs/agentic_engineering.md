# Как проектом управляли, а не «вайбкодили»: ответы на вопросы защиты

Четыре вопроса с защиты и ответы на них со ссылками на конкретные файлы и коммиты — чтобы процесс был виден в репозитории, а не только в презентации.

## 1. Архитектура — как выбрали и почему именно такую

Архитектура выбиралась не «по умолчанию» агентом, а через **жёсткие ограничения → отсев → сравнение** (метод, отработанный в ДЗ-1 на выборе AI-инструмента, см. раздел 1 [backend_documentation.md](../backend_documentation.md)).

| Решение | Альтернативы | Почему так | Где зафиксировано |
|---|---|---|---|
| **Supabase** (PostgreSQL + Auth + RLS + Storage) | Self-hosted: Node/Express + Postgres в Docker на VPS | На рабочей машине нет прав администратора → Docker недоступен; VPS нет. Supabase даёт Auth, RLS и REST API без собственного сервера — для команды из одного человека это единственный способ получить production-бэкенд за разумное время | `backend_documentation.md` §1 (таблица сравнения) |
| **Безопасность в БД, а не в middleware** (RLS, права уровня колонок, `security definer` RPC) | Проверки прав в собственном API-слое | Без своего сервера единственная граница доверия — PostgreSQL. Поэтому правило «подписать можно только через подтверждение» живёт в `sign_document()` и column-grants, а не в React-коде, который клиент может обойти | миграции 1, 3, 4; `security_audit.md` |
| **Интерфейс `EdoProvider`** между UI и данными | Прямые вызовы supabase-js из компонентов | Три причины: (а) мок-реализация → тесты и CI без секретов; (б) бэкенд подключили в ДЗ-5 **не меняя ни одного компонента** ДЗ-4; (в) анализ конкурентов назвал главным риском зависимость от API одного ЭДО-провайдера — абстракция уже была готова | `src/types.ts`, `src/api/index.ts`, `docs/competitors.md` вывод 5 |
| **GitHub Pages + HashRouter** | Vercel/Netlify + BrowserRouter | Pages не требует второго аккаунта и токенов (деплой по OIDC); цена — нет SPA-fallback → HashRouter. Осознанный компромисс, задокументирован в `src/App.tsx` | `integration_documentation.md` §1 |
| **Чистая логика отдельно от React** (`src/lib`) | Логика внутри компонентов | Правило 3 `CLAUDE.md` — чтобы фильтры, валидация, разбор ошибок OAuth тестировались юнитами без DOM | `src/lib/*.test.ts` |

Решения принимались человеком; агент предлагал варианты и аргументы, но, например, выбор Google вместо Яндекс ID для OAuth — моё решение по причине «у Supabase нет встроенного Яндекс-провайдера, а своего бэкенда для обмена кода нет».

## 2. CI/CD — что применено из курса, а не «сгенерировано по умолчанию»

Да, первый вариант `ci.yml` сгенерирован агентом по промпту. Но промпт содержал требования из курса, а дальше пайплайн **дорабатывался по результатам прогонов**:

| Принцип | Как реализован | Что показал на практике |
|---|---|---|
| **Fail-fast: дешёвое раньше дорогого** | порядок шагов `audit → lint → prettier → tsc → test → build` | прогон 4–5 упал на `prettier --check` за 20 секунд, не дойдя до сборки |
| **Деплой зависит от качества** | `needs: quality`, деплой только для `main`, не для PR | job `deploy` был пропущен при падении форматирования — «красное» не попало на сайт |
| **Отмена устаревших прогонов** | `concurrency: ci-${{ github.ref }}` + `cancel-in-progress` | при двух пушах подряд первый прогон отменяется |
| **Секреты ≠ переменные** | ключ Supabase — в Secrets; URL сайта, health-URL, счётчик Метрики — в Variables | публичные значения видны в логах, секреты — нет |
| **Без долгоживущих токенов** | деплой через OIDC (`id-token: write`), а не через PAT в секретах | нечего утечь |
| **Проверка после публикации** | smoke-check `curl` живого URL в job `deploy` | первый деплой упал, потому что Pages не был включён — пайплайн это показал, а не «прошёл» |
| **Post-deploy e2e (добавлено по замечанию защиты)** | job `verify`: Chrome на runner'е → вход на production → лента из Supabase → журнал (`scripts/e2e-smoke.mjs`) | закрывает разрыв «деплой зелёный, приложение не работает» — именно так проявились кейсы 4–5 |
| **Мониторинг как код** | `uptime.yml` по cron каждые 30 минут: health RPC + сайт; падение = письмо от GitHub | отработал в первом же ручном запуске |
| **Воспроизводимость** | `npm ci` с lock-файлом, кэш npm, пин версий actions; локально тот же набор — `npm run ci` | локальный и CI-прогоны совпадают |

Чего в пайплайне нет сознательно: Docker-образов (нет сервера, который их запускал бы) и матрицы Node-версий (один runtime в production).

## 3. Что значит «подписание через диалог»

Формулировка неудачная, точнее — **«подписание только через явное подтверждение»**. Смысл в трёх слоях, каждый из которых проверяем:

1. **UI-слой.** Кнопка «Утвердить и подписать» не подписывает. Она открывает диалог ([`SignDialog.tsx`](../src/components/SignDialog.tsx)), где показаны документ, контрагент, сумма и подписант, и только кнопка «Подтвердить» в этом диалоге вызывает `provider.sign()`. Это правило 8 [`CLAUDE.md`](../CLAUDE.md): «кодового пути „подписать без подтверждения" не существует». Тест: «„Отмена" в диалоге не меняет статус документа» ([`App.test.tsx`](../src/App.test.tsx)).
2. **Слой данных.** Даже если обойти UI, клиент не может выставить `status = 'signed'`: у роли `authenticated` отозван `UPDATE` на колонку `status` (миграция 1, права уровня колонок). API-тест №4: прямой `PATCH status` → 403.
3. **Слой бизнес-правил.** Единственный путь — RPC `sign_document()` (`security definer`), которая проверяет членство, роль `signer`, статус документа, блокирует строку (`for update`) и пишет попытку в append-only журнал — включая отказы. API-тесты №6–9.

Откуда правило: из проекта-предшественника (ДЗ-2, Telegram-бот для Диадока) — там «никогда не подписывать автоматически» было правилом 8 для AI-агента, потому что подпись юридически значима. Здесь оно перенесено с уровня инструкции агенту на уровень архитектуры.

## 4. Agentic engineering, а не вайбкодинг — чем отличается и где следы

Вайбкодинг — «попросил, получил, запустил, работает — следующий промпт». Признаки инженерного управления агентом — заранее заданные правила, независимая проверка результата, воспроизводимые проверки и журнал решений. По каждому признаку — где это лежит в репозитории:

| Признак | Вайбкодинг | В этом проекте | Следы в репозитории |
|---|---|---|---|
| **Правила до кода** | агент пишет «как получится» | системные правила проекта: роль, стек, 4 состояния экрана, запрет `any`, подписание только через подтверждение, тесты по ролям | [`CLAUDE.md`](../CLAUDE.md) (11 правил); правило 7 породило `src/lib/*` с юнитами, правило 8 — RPC на уровне БД |
| **Структурированные промпты** | свободный чат | шаблоны Role-Task-Context-Format из ДЗ-2 для генерации, рефакторинга, тестов, багфикса, декомпозиции | промпты процитированы в [`development_process.md`](development_process.md) и `integration_documentation.md` §1.1 |
| **Агент проверяет агента** | автор верит своему выводу | ТЗ проверено независимым агентом-«техлидом» (5 критичных пробелов); аудит безопасности независимым агентом (12 находок); анализ конкурентов — субагент с веб-поиском | [`security_audit.md`](../security_audit.md) (полный отчёт агента + таблица «находка → исправление → статус»), [`competitors.md`](competitors.md), ТЗ v1.1→1.3 в репозитории ДЗ-3 |
| **Верификация другим инструментом** | «запустил — вроде работает» | 43 юнит/компонентных теста; 10 API-тестов против живой базы (5 негативных); 6 e2e-сценариев puppeteer на production; скрипт «свежий пользователь с нуля»; CI-гейты | `src/**/*.test.ts(x)`, [`scripts/api-tests.sh`](../scripts/api-tests.sh) + `docs/api-tests-output.md`, `scripts/e2e-*.mjs`, `scripts/screenshots-prod.mjs`, `.github/workflows/` |
| **Баги ловит проверка, а не удача** | баг замечает пользователь | 5 багов прошли через зелёные тесты и «Success» миграций и были пойманы только верификацией на живой системе; каждый задокументирован с причиной | [`development_process.md`](development_process.md) кейсы 1–5; миграции 2, 5, 6 с объяснением в шапке |
| **Журнал решений** | решения нигде | каждая миграция начинается с «почему»; в коде — комментарии только о неочевидных ограничениях (не «что делает строка») | `supabase/migrations/*.sql` (шапки), `src/App.tsx` (HashRouter), `src/api/supabaseProvider.ts` (почему `{ok,error}` вместо исключения) |
| **История изменений читаема** | один коммит «final» | 25+ коммитов с атомарными сообщениями по-русски, каждый — законченный шаг с зелёным CI; трейлер `Co-Authored-By: Claude` — честная пометка соавторства | `git log --oneline` |
| **Границы ответственности человека** | «AI сделал» | человек: выбор архитектуры и провайдеров, применение миграций в production, создание аккаунтов и ключей, приёмка каждого этапа, решения по находкам аудита (одна принята с оговоркой); агент: генерация, рефакторинг, тесты, поиск причин ошибок | `security_audit.md` (F-06 «принято с оговоркой»), `backend_documentation.md` §3 |
| **Честность о пределах** | «всё работает» | в отчётах названо, что НЕ сделано и почему: нет SQL-тестов RLS в CI, нет Docker, платежи не интегрированы, мобильная версия — адаптив, не приложение | `security_audit.md` «рекомендации», `integration_documentation.md` §1.4 |

**Что я бы назвала главным отличием.** В вайбкодинге цикл замыкается на «работает ли с виду». Здесь цикл замкнут на проверке, которую делает *не тот, кто генерировал*: другой агент (ревью ТЗ, аудит), другой инструмент (API-тесты, e2e, живая база), другой сценарий (свежий пользователь). Пять из пяти серьёзных багов проекта найдены именно так — и ни один из них не нашёл бы «вайбкодинг», потому что всё было зелёным.

**Что осталось от вайбкодинга, честно:** первые версии `ci.yml` и UI-компонентов — чистая генерация по промпту; их инженерная ценность появилась после прогонов, замечаний линтера и ревью. Разница не в том, что агент не генерировал, а в том, что сгенерированное не считалось готовым, пока не прошло независимую проверку.
