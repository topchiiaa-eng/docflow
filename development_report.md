# Отчёт о разработке: «ДокПоток» (фронтенд) с AI-агентом

**Агент:** Claude Code (Claude Fable 5) · **Правила проекта:** [CLAUDE.md](CLAUDE.md) (адаптация файла правил из ДЗ-2) · **ТЗ:** «ДокПоток» v1.3 из ДЗ-3.

## Как шла разработка (по шагам задания)

### Шаги 1–2. ТЗ и инициализация

За основу взято ТЗ v1.3 из ДЗ-3; стек зафиксирован по его разделу 6: React + TypeScript (strict), Tailwind CSS, Vitest. Агент проверил доступность npm-registry (`npm ping`), инициализировал проект (`npm create vite@latest docflow -- --template react-ts`), поставил зависимости, настроил `vite.config.ts` (плагины react + tailwindcss, секция vitest с jsdom) и hot reload через dev-сервер. Файл правил из ДЗ-2 применён как `CLAUDE.md` в корне проекта, адаптированный под фронтенд (запрет `any`, обязательные 4 состояния экрана, «подписание только через диалог» — наследие правила 8, тесты по ролям, а не CSS-классам).

### Шаги 3–4. Структура и компоненты

Промпт по шаблону 5 из ДЗ-2 (декомпозиция) дал структуру: чистая логика в `src/lib` (без React — тестируется юнитами), доступ к данным через интерфейс `EdoProvider` (внедряется в `App` пропом — это позволило тестам подменять провайдер), компоненты по файлу на каждый. Роутинг не потребовался: приложение одноэкранное (master-detail), что зафиксировано осознанным решением.

Компоненты генерировались промптами по шаблону 1 из ДЗ-2 (Role-Task-Context-Format), например:

> **Role:** Senior Frontend-разработчик (задан CLAUDE.md). **Task:** реализуй панель карточки документа: атрибуты, PDF-плейсхолдер, кнопка «Утвердить и подписать» только для статуса requires_signature, состояния signing/error. **Context:** типы в `src/types.ts`, стиль — Tailwind, светлая тема концепции «Дашборд» из ДЗ-3. **Format:** один файл `DetailPanel.tsx`, тексты на русском, минимальный дифф.

Mock-данные (`fixtures.ts`) включают спецслучаи для проверки состояний: документ без суммы (прочерк), документ `doc-fail` (гарантированная ошибка подписания), URL-параметр `?fail=1` (отказ загрузки).

### Шаг 5. Тестирование и отладка — главный урок ДЗ

**Реальный баг, найденный техниками из задания.** После первого запуска скриншот приложения показал вечное «Загружаем документы…», а страница `?fail=1` не показывала error-state. Отладка шла ровно по методике задания:

1. **Анализ скриншота (мультимодальность):** на снимке headless-браузера видно застрявший loading-spinner — значит, промис не завершается или состояние не обновляется.
2. **Интерпретация консоли:** `read_console_messages` показал **бесконечный поток** одинаковых ошибок `listIncoming failed` — не «одна ошибка без обработки», а цикл перезагрузки.
3. **Генерация исправления:** диагноз агента — классическая React-ловушка: дефолт пропа `provider = createMockProvider()` создаёт **новый объект при каждом рендере** → `useCallback([provider])` пересоздаёт `load` → `useEffect([load])` запускает загрузку заново → бесконечный цикл. Исправление — единственный экземпляр провайдера на уровне модуля (минимальный дифф в 3 строки, зафиксирован комментарием в `App.tsx`).

**Почему тесты этот баг не поймали:** тесты передают провайдер пропом — стабильной ссылкой, поэтому цикла в них нет. Это то же наблюдение, что и в ДЗ-1: зелёные тесты проверяют то, о чём автор подумал; баг жил ровно в той конфигурации (дефолтный проп), которую тесты не использовали. Ловится такой класс багов только запуском настоящего приложения.

**Автотесты:** 12 штук — 6 юнитов чистой логики и 6 компонентных сценариев, у каждой ключевой функции есть негативная ветка (пустой результат фильтра, отказ загрузки + «Повторить», отмена диалога, ошибка провайдера при подписании со счётчиком «статус не изменился»). Все проходят: `Tests 12 passed (12)`.

### Шаг 6. Адаптивная вёрстка

Брейкпоинты Tailwind: `lg` (1024px) переключает master-detail на оверлей поверх списка, `sm` перестраивает KPI-плитки из колонки в ряд. Проверка — скриншоты 1280×800 и 375×812 (эмуляция мобильного вьюпорта в puppeteer с `isMobile/hasTouch`): [docs/screenshots](docs/screenshots). На мобильном длинные названия контрагентов обрезаются `truncate` — переполнений нет.

### Шаг 7. Рефакторинг и оптимизация

- Выделение `filterDocuments`/`kpi`/`formatSum` в чистый модуль сделало их переиспользуемыми (KPI и лента считают из одного места) и дёшево тестируемыми.
- `useMemo` для фильтрации и списка организаций — чтобы не пересчитывать на каждый ввод в несвязанные поля.
- Производственная сборка: 205 КБ JS (64 КБ gzip) — без дополнительных оптимизаций уложились в разумный размер.

## Проблемы и решения (сводно)

| Проблема | Как решили |
|---|---|
| Бесконечный цикл загрузки (нестабильный дефолт пропа) | Диагностика по скриншоту + консоли; провайдер вынесен на уровень модуля |
| Headless-скриншот ловил loading-state | Сначала пробовали `--virtual-time-budget`; с dev-сервером не работает — **HMR-вебсокет не даёт странице «затихнуть»**, виртуальное время не движется и процесс висит. Решение: скрипт на `puppeteer-core` с системным Chrome и явным `waitForSelector` по тексту данных |
| Тесты не поймали цикл перезагрузки | Осознано ограничение: DI-проп в тестах ≠ дефолтная конфигурация; добавлена ручная проверка приложения в браузере как обязательный шаг |

## Какие техники оказались самыми эффективными

1. **Консоль браузера > скриншот** для диагностики: скриншот показал «что сломано» (вечная загрузка), но именно лог консоли показал «почему» (повторяющиеся ошибки = цикл). Связка обоих — быстрый диагноз.
2. **Внедрение зависимости провайдера** — одно архитектурное решение дало и тестируемость (подмена в тестах), и демо-режимы (`?fail=1`), и готовность к реальному API.
3. **Правила проекта (CLAUDE.md) как чек-лист качества:** «4 состояния экрана обязательны» и «подписание только через диалог» не потребовали ни одной итерации доработки — они были заложены в первые же версии компонентов.
4. **RTCF-промпты из ДЗ-2** сократили итерации: компоненты, сгенерированные с явным Context (типы, тема, соглашения), не потребовали переделок под стиль.

## Выводы

Приложение реализует 3 основные функции ТЗ, адаптивно, покрыто 12 тестами, содержит задокументированный кейс реальной отладки с AI. Главный перенесённый через все четыре ДЗ вывод подтвердился и здесь: генерация кода — быстрая часть работы; ценность агента в том, что он умеет *проверять сам себя разными инструментами* (тесты + запуск + скриншоты + консоль), но финальную ответственность за «работает по-настоящему» несёт запуск реального приложения, а не зелёный прогон тестов.
